# Capture specification

## Baseline before Friends release

Source audited at plugin `864a94d` and ingest `5658449`. This describes the checked-in code, not production records. The data flow is plugin → `web.xivforays.com/api/forays/` → MongoDB → BestiaryGeneration.

Both uploads require **Allow crowdsourcing** (off on a fresh config) and game collection requires a loaded local player in a matching territory and map. The baseline uses localized place-name substring checks for Eureka, Zadnor, Bozjan Southern Front and South Horn. The base URL is configurable. Every POST uses JSON (camelCase on the wire), `X-Api-Key` and `User-Agent: XivForays/<assembly version>`. No durable upload spool exists.

| Endpoint and shape | Trigger and frequency | JSON fields |
| --- | --- | --- |
| `POST /enemyposition`, array of objects | About every 5 seconds, the plugin enumerates combatant battle NPCs with positive HP and queues a nonempty snapshot. Every 3 seconds a worker attempts one batch, requeues errors and clears the queue above 10 batches. A dead NPC still present in the object table can appear as a stale row until removed. | `mobIngameId` (NPC base ID, not its runtime object ID), `mobName`, `level` (native ForayInfo level on first sight; zero can persist), `x`, `y`, `z` (world coordinates), `isAdapted`, `isMutated`, `timeStamp` (UTC epoch seconds), `element` (native numeric code as text), `isInCombat` (has target or missing HP), `hasBeenInCombat` (observed earlier), `territoryId`, `mapId`, `instanceId` (random local visit GUID). |
| `POST /fateended`, one object | Polls the FATE table every 500 ms. Tracks a Running entry with positive start epoch and nonzero position. Queues it when Ended, Failed or missing from the table, provided the territory still matches. A worker tries one row every 2.5 seconds and requeues errors. | `fateId`, `name`, `x`, `y`, `z`, `radius`, `startedAt` (game epoch seconds), `endedAt` (observed UTC epoch seconds), `instanceId` (separate random local visit GUID), `territoryId`, `mapId`, `levelId` (FATE level), `reward` (always null on this path). |

The baseline has no FATE start/progress upload. The reward module returns before it activates. The diagnostic module subscribes locally to chat and inventory changes and can log matching chat text, sender, inventory changes and FATE reward diagnostics. It does not upload them. The baseline also logs the plugin's API key locally, and the ingest service logs the key, raw request body, FATE account association and Mongo connection string.

## Baseline ingest

`ApiGuidMiddleware` checks the GUID key against the enabled keys in the account database. `ForaysController` binds a typed DTO for each POST and `MongoService` maps it into `MongoEnemyPosition` (one document per array entry) or `MongoFate` (one document per completion). Mongo fields use PascalCase and omit the unused FATE reward. Each document gets a Mongo `_id`, `OwnerKey` (the authenticated key in GUID-string representation) and `PluginVersion` (from the User-Agent). `InstanceId` is also a GUID string. Legacy uploads are append-only and can duplicate on retry after an ambiguous response.

## Baseline BestiaryGeneration reads

- `Infrastructure/CloudMongoClient.cs` opens the configured cloud collections, defaulting to `MongoEnemyPosition` and `MongoFate` in `Configuration/CloudMongoOptions.cs`.
- `Pipeline/Bestiary/BestiaryCommand.cs` uses `MongoEnemyPositionAggregateSource` in `Pipeline/Bestiary/IEnemyPositionAggregateSource.cs` for the Mongo source. It matches territory, groups by base ID, name, level, element and mutation/adaptation flags, and counts documents and distinct visit IDs. It does not use raw XYZ or loot to select the bestiary level.
- `Pipeline/Fates/IFateRecordSource.cs` streams Eureka territory IDs 732, 763, 795 and 827. It reads document and owner IDs, visit ID, territory, FATE ID/name, XYZ, radius, start/end, map and level. `CloudEnemyPositionRepository` and `CloudFateRepository` also serve typed reads for older paths. These types do not declare the new observation fields or an ignore-extra-elements attribute.
- BestiaryGeneration also has local Mongo collections, cloud sync code and log-based analysis paths. This release leaves BestiaryGeneration read-only and does not execute those paths.

## Gaps and why they matter

| Gap | Why it matters |
| --- | --- |
| Enemy elemental level | A zero or stale value leaves many Eureka enemies without a reliable level and makes comparisons to player level unreliable. |
| Player elemental and effective sync level at kills and loot | Separates level-gap effects from synchronization when measuring where drops stop. Requires explicit kill/loot attribution, including no-drop kills. |
| Mutation and adaptation | Base and transformed mobs need separate level/drop distributions. The baseline selects one status and misspells the name in the adaptation branch. |
| Weather on each observation | Allows weather-conditioned spawns, transformations and rewards to be compared. |
| Enemy appearance, disappearance and movement | First/last visible positions and paths help distinguish spawn points, roaming and possible respawn timing. Client visibility alone cannot prove server spawn or despawn. |
| FATE start, update and end with centre/radius | Supports overlap, geography, progress and duration analysis. Missing visibility must be distinguishable from a confirmed end. |
| Coffer, bunny, pot and carrot positions and grades | Maps find/reward locations and helps separate routes and rewards by grade. |
| Chain number | Separates chain effects from level, weather and mutation effects in drop analyses. |
| Occult Crescent knowledge levels and Critical Encounters | Enables later comparisons of enemy/reward level gaps and CE timing and geography. |

## Friends release capture

Recording remains opt-in. The zone gate (`Core/ForayZones.cs`, 0.0.0.12) uses territory IDs for the four Eureka zones (732, 763, 795, 827), Bozjan Southern Front (920), Zadnor (975), Delubrum Reginae normal and Savage (936, 937) and both Occult Crescent Horns (1252, 1346). Any map layer owned by the zone is accepted: the Baldesion Arsenal (maps 520-527 in 827), Castrum Lacus Litore (616 in 920), the Dalriada (673-675 in 975), the Delubrum floors (641-647, shared by 937) and the Forked Tower (Tower of Blood 968-990 in 1252, Tower of Magic 1136-1191 in 1346). Eureka Orthos (1099-1108, 1124) is excluded. A loaded character outside zone transitions is required. `XivForays.Plugin.Tests/GameSheetTerritoryTests.cs` checks the IDs against the local game sheets. A shared random visit ID resets at territory changes. It identifies one recorder's visit, never a shared server instance. No transition synthesizes a kill or event end.

The original two POST routes retain their JSON shape and collection layout. Live enemy rows refresh the native foray level at each sample and drop stale dead rows. Zero still means the native value is unavailable. Mutation and adaptation are checked independently against status IDs resolved from the English game sheet. The legacy FATE endpoint still accepts observed disappearance as a completion and uses the initial centre and radius for compatibility.

### Versioned observations

`POST /api/forays/observations` carries an object with `schemaVersion: 1`, a random `batchId` GUID and an `observations` array of 1–256 typed records. JSON property names use camelCase. Omitted optional fields mean unavailable or inapplicable. Every record carries numeric `kind`, `observedAtMs` (UTC Unix milliseconds), `visitId`, `territoryId`, `mapId` and optional `weatherId` (the live client weather row). In Eureka, player context includes current and effective elemental levels and a synced flag when available. In Occult Crescent, it includes current and effective Knowledge Levels. Both values come from the game's content-value keys. No generic job level substitutes for an unavailable elemental or Knowledge Level.

| Kind | Trigger and specific fields |
| --- | --- |
| 1–4 enemy appeared / sampled / died / disappeared | Scan every 500 ms (local). A sample is recorded only when elemental/Knowledge Level, mutation/adaptation, model ID or scale changes, when the enemy moved 15 yalms since its last record, and once every 30 seconds per live enemy (0.0.0.12; was every 5 s). Includes base ID (`gameId`), random `enemyTrackId`, XYZ, `modelCharaId` and `modelScale` (0.0.0.12), applicable elemental/Knowledge Level and element ID, combat level, mutation/adaptation flags and current combat heuristic. A visible transition to zero HP produces a death. Disappearance uses the last observed XYZ and the time/weather when loss was noticed. Visits do not share enemy IDs. |
| 5–8 FATE first seen running / updated / terminal / disappeared | Poll every 500 ms. Includes FATE ID, observed centre/radius, game start epoch seconds, progress and state. Emits an update on progress or geometry changes. Ended/Failed is terminal. A missing or replaced entry is a separate observation. |
| 9 loot | A recognized English self-award notice on the loot channel with a single structured item link contributes item ID and quantity where the notice exposes it. Includes current player-level/weather context. Does not assign the item to a kill, FATE or chest. From 0.0.0.15 (captureRevision 4): `noticeRow` (LogMessage row 657/3538/3599, absent on the English fallback), the player's `chainNumber` (last chain notice while the chain timer runs, 0 = no chain) and `chainAgeMs`; `defeatTrackId` / `defeatAgeMs` / `defeatBy` of the latest kind 13 at most 5 s earlier (`defeatTrackId` absent when that defeat's enemy was not found); `fateRewardId` when a FATE in the zone reached 100 % or Ended in the last 5 s (nearest to the player). A record with `fateRewardId` never has a defeat link. Loot after a defeat whose enemy is still being looked up (up to 1.5 s) is sent after it, with its original `observedAtMs`. |
| 10 chain | A recognized English self-sourced EXP chain notice on the system-error channel contributes the chain number and current context. Does not assign it to an enemy. From 0.0.0.15: `defeatTrackId` / `defeatAgeMs` / `defeatBy` as on kind 9 (no FATE guard), so each chain number joins its kill. |
| 11 treasure | Poll every second. Reports recognized coffers, Happy Bunnies, pots and carrots by base ID and world XYZ, on first visibility or movement of at least two world units. `treasureKind` 1/2/3/4 means coffer/bunny/pot/carrot. `treasureGrade` 1/2/3 means bronze/silver/gold where the model or static name identifies it. Missing grade means unknown or inapplicable. |
| 12 Critical Encounter | Poll native dynamic events every second in the Horns and, from 0.0.0.12, in Bozjan Southern Front and Zadnor (the Bozja director's `DynamicEventContainer`; verify in game). Emits first visibility, changed state/start/progress/geometry and an inactive edge if an entry disappears. Includes dynamic event ID, native start timestamp, seconds left when present, progress, state and marker centre/radius when populated. State values 0/1/2/3 mean inactive/register/warmup/battle. |
| 13 self defeat | A recognized English self-sourced defeat notice targeting an enemy contributes a self-defeat signal with player levels and weather. The enemy name in the notice is discarded and this signal has no enemy ID or claimed loot link. From 0.0.0.15 (row 557): also a party member's defeat, with `defeatBy` 1 = own, 2 = party member (category only; the party member is compared in memory and never sent; other players' defeats are not recorded). The enemy is found among enemies at HP 0 by the notice's name row (ObjStr id, a BNpcName row), retried for up to 1.5 s, freshest death then nearest: `enemyTrackId`, `gameId`, `layoutId`, `form` (bits 1 mutated, 2 adapted), `isMutated` / `isAdapted`, levels, XYZ, `fateId`, `enemyMatch` (0 none, 1 name unique, 2 name nearest, 3 no name match unique, 4 no name match nearest) and `enemyCandidates`. |
| 14 recording active (0.0.0.12) | Every 30 seconds while recording: the local player's own XYZ plus the shared context (zone, map, weather, EL/KL, visit ID). No name, content ID, job or world. Absence of a spawn while heartbeats exist means someone was watching. From 0.0.0.15: `lootListening` (the loot and defeat notice hook is attached), so a kill with no loot record can count as "no drop". |

The worker attempts one batch every two seconds. From 0.0.0.12, 5xx, 408, 429, timeouts and network errors retry the same batch with exponential backoff (2 s doubling to 5 min, given up after 8 attempts); other 4xx drop the batch; 401/403/404 drop it and pause that stream for 5 minutes, and a 404 logs one warning that the web friends branch is not deployed. The legacy routes use the same policy; the legacy enemy snapshot is now every 15 s (was 5 s). The in-memory queue retains up to 4,096 pending events plus one retry batch. Older pending events are dropped if it fills. Unsupported or rejected batches are dropped independently of legacy uploads. A failed transport retries the same batch ID. Disabling sharing discards pending data and cancels outstanding client requests; the server may already have received a request. MongoDB stores one document per batch in `MongoForayObservationBatch`. Its deterministic `_id` combines a SHA-256 reference derived from the authenticated GUID and the batch ID so replay of the same batch is idempotent. Fields use PascalCase. BestiaryGeneration does not read this collection yet. No migration or backfill is required.

### Remaining evidence gaps

- An enemy with zero native foray level remains unknown. Check late-loaded, mutated and adapted enemies in game before treating reported levels as complete.
- Brief visibility between polls, deaths outside view, and IDs recycled between polls can be missed. Appearance/disappearance can mean draw range or a visibility change. A visible death does not prove recorder or party credit.
- A controlled run is still needed to establish all credited kills, per-species no-drop denominators and exact kill/loot/chain joins. The English notice filters can miss other client languages and award formats. Treasure sightings do not establish a specific hunt, owner, opening or award.
- Confirm treasure recognition, CE marker geometry and knowledge/elemental sync values in the client. CE samples distinguish registration from battle. An inactive edge records disappearance, which may have other causes than successful completion.
